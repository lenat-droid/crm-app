# 一线 BD 视角：现状摸底报告

## 1. 线索管理 `/leads`

### 录入表单（`src/app/leads/new/page.tsx`）
单页一次性表单，**8 个字段，只有「商家名稱」必填**：

| 字段 | 控件 | 必填 |
|---|---|---|
| name 商家名稱 | Input | ✅ |
| phone 電話 | Input | |
| contactPerson 聯繫人 | Input | |
| foodType 餐飲類型 | Input（**自由文本，无下拉**） | |
| posBrand POS 品牌 | Input（自由文本） | |
| needs 需求描述 | TextArea | |
| visitDate 拜訪日期 | DatePicker | |
| notes 備註 | TextArea | |

后端校验一致：`src/lib/validation/schemas.ts:130-144`（`validateCreateLead`），仅 `name` 用 `assertString`，其余全 optional。表单里没有暴露 `source`（线索来源）和 `score`，但 API 接受（schemas.ts:140-141）——**字段在 schema 里存在但 UI 不可填**。

### 流程步数
**1 步**，无分步向导。提交后 `router.push('/kanban')`（leads/new/page.tsx:32），即 BD 提交后被弹到看板，**不回线索列表也无法连续录入下一条**（对比 `/quick-checkin` 有「继续登记」）。

### 列表展示与筛选（`src/app/leads/page.tsx`）
- 列：名稱 / 電話 / 聯繫人 / 餐飲類型 / 需求 / 狀態 / 登記人 / 日期 / 操作，`scroll={{x:1100}}`，分页 20。
- **筛选器：完全没有**。没有搜索框、没有状态筛选、没有日期范围、没有导出。API `src/app/api/leads/route.ts:15,22` 其实支持 `?status=`，但前端从未传。
- 数据权限：`role === 'SALES'` 只看自己登记的线索（api/leads/route.ts:19-21）。

### 转化机制
**已「自动转化」，实际上等于取消了线索阶段**：`src/app/api/leads/route.ts:56-102` 在一个事务里同时创建 Lead(`status:'converted'` 硬编码，第 66 行) + Customer(`source:'LEAD_CONVERSION'`) + Pipeline(`status:'已建联'`)。页面上还写着提示「新建線索時自動創建客戶 + Pipeline，無需手動轉化」(leads/page.tsx:105)。

手动转化 `action:'convert'` 的老逻辑仍保留在 PATCH（route.ts:126-162），但**前端已无任何入口调用它**（列表「操作」列只有「查看客戶」）。

### 状态流转
`Lead.status` 定义了 `new / contacted / converted / closed`（schema.prisma:240），列表也做了 4 色 Tag（leads/page.tsx:12-24），但：
- POST 永远写死 `'converted'`；
- 前端没有任何改状态的 UI（无下拉、无按钮）；
- 结果：**线索状态字段事实上是死的，所有线索都是「已轉化」**。连带影响 Dashboard 的「待處理線索」统计（dashboard/page.tsx:105，数据来自 `lead.groupBy(['status'])`）——恒为 0。

真正的阶段流转发生在 **Pipeline**：`⚠️待跟进 / 已建联 / 初步有意向 / 合作中`（schema.prisma:159、kanban/page.tsx:17-22、165），通过看板卡片上的 Select 切换（kanban/page.tsx:323-330，**不是拖拽**），关闭时区分 WON/LOST（kanban/page.tsx:82-107）。

## 3. 拜访记录 `/visits` 与统一记录 `/records`

BD 记录一次沟通有 **3 条互相独立的路径**（`src/components/RecordTypeNav.tsx` 用 Segmented 把它们并列）：

| 入口 | 落库模型 | 需要填 |
|---|---|---|
| `/leads/new` | Lead + Customer + Pipeline | 8 字段，只 name 必填 |
| `/quick-checkin`「每日速报」 | **Communication**（挂 Pipeline） | 选客户 + 日期 + 记录文本 + 可选调 7 个产品意向 |
| `/visits/new`「拜訪記錄」 | **Visit** | customerId(必填) + visitDate(必填) + outcome(下拉) + notes |

### 关联方式
- `Visit.customerId` 必填 → **只能关联已存在客户，不能对线索/陌拜新店直接记拜访**（visits/new/page.tsx:71-79）。
- 客户下拉一次性拉 `pageSize=100`（visits/new/page.tsx:24），`onSearch` 只在这 100 条里做前端 filter（第 30-32 行）——**客户数上千时搜不到人**。相比之下 quick-checkin 的选择器是走服务端 search 的（quick-checkin/page.tsx:48-61）。
- `Communication` 挂在 `Pipeline` 上，Pipeline 唯一挂 Customer；`/api/pipelines` POST 会顺带更新 `pipeline.lastContactDate`（api/pipelines/route.ts:73,80）。
- `/records`（`src/app/records/page.tsx` + `api/records/route.ts`）把 lead / communication / visit 三种归一化成时间线，Segmented 按类型过滤。**注意 api/records/route.ts:44-83 是把三张表全量取出再在内存里 sort+slice 分页**（第 129-135 行），数据量上来会有性能问题；且该页**只有类型筛选，没有日期、客户、人员筛选**。

### 跟进闭环
**基本不存在**：
- `Visit` 模型（schema.prisma:189-199）只有 visitDate/outcome/notes，**没有 nextFollowUpDate**。
- `Communication`（177-187）只有 contactDate/record/contactOrder。
- 全仓库 grep `nextFollow / followUp / reminder / task / 待办 / 下次跟进` → **源码零命中**，只在 `docs/requirements.md:1317` 有个「Phase 3 待办」章节标题误命中。
- 看板卡片只显示「最近聯繫: MM-DD」（kanban/page.tsx:318），**没有「多久没联系」的过期高亮，也没有按 lastContactDate 排序**。
- `⚠️待跟进` 只是 Pipeline 的一个手动列，**不会自动把超期客户挪进来**。
- Dashboard（`src/app/dashboard/page.tsx`）全是总量统计（客戶總數/MRR/活躍訂閱/跟進中 Pipeline/待處理線索/拜訪記錄），**没有「我今天该跟谁」的待办列表**。

## 4. Prisma schema 关键结论（`prisma/schema.prisma`）

| 模型 | 行 | 与跟进相关的字段 |
|---|---|---|
| `Lead` | 230-249 | `status`(new/contacted/converted/closed)、`source`、`score`、`visitDate`(**历史拜访日，不是下次跟进**)、`registeredById`、`customerId` |
| `Customer` | 39-97 | `contactStatus`、`lastActivityAt`(只被 customer-health 读，**没有任何写入点**)、`followerId`、7 个 `*Status` 产品意向 |
| `Pipeline` | 153-175 | `status`(4 阶段)、`active`、`closedAt`、**`lastContactDate`（唯一的时间线索，且只有「上次」没有「下次」）** |
| `Communication` | 177-187 | contactDate / record / contactOrder |
| `Visit` | 189-199 | visitDate / outcome / notes |
| `VisitLog` | 201-228 | 一张很详细的「踩店问卷」（POS 品牌/月费/费率/合同到期、扫码点餐、Kiosk、摄像头、漏接电话、最大痛点、`posDevicePhoto`/`menuBoardPhoto` 照片字段） |

**明确缺失**：
- ❌ 无「下次跟进时间」字段（任何模型都没有）
- ❌ 无 Task / Reminder / Todo / Activity 模型
- ❌ 无逾期/SLA 概念，无通知表
- ⚠️ 阶段流转有两套并存：`Lead.status`（已死）与 `Pipeline.status`（在用），语义重叠且不互通
- ⚠️ **`VisitLog` 是孤儿模型**：只在 `src/app/api/customers/[id]/route.ts` 被 include 读取、在 `src/app/api/admin/import/route.ts` 被批量导入写入，**没有任何创建 UI**，`/visits/new` 写的是简版 `Visit` 而不是它。BD 在店里最该采集的 POS 合同到期日、月费、痛点、照片全都填不了。
- ⚠️ `src/app/api/upload/route.ts` 存在（写 `public/uploads`），但全仓库 **没有任何前端调用** → 照片字段无上传入口。

## 体验痛点汇总（按对 BD 的影响排序）
